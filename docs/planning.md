# 第二阶段：任务规划与固定快照对照

本阶段实现人工或模型生成的任务 DAG、静态调度和基于来源覆盖代理的自适应调度。
在线初始任务分解已通过 `--auto-plan` 接入（见 [自动规划说明](auto-planning.md)）；尚未实现运行中增删任务、冲突检测、Reflection 或完整 EAAP。

## 任务输入

`Plan` 包含研究问题和子任务；每个子任务包含：

| 字段 | 含义 |
| --- | --- |
| id / description | 稳定标识与研究目标 |
| queries | 有序备选查询；空结果或读取失败后可以尝试下一查询 |
| dependencies | 先决任务；必须达到来源阅读目标才放行 |
| target_sources | 希望阅读的不同 URL 数量 |
| priority | 人工优先级，默认 1；对照时两种策略使用同一份配置 |

加载时拒绝循环依赖、未知依赖、重复 ID、空查询和跨任务重复查询。
跨任务重复查询目前不支持；不同查询返回同一 URL 时会复用来源和已阅读正文。
同一来源可关联多个任务，这种关联只表示检索来源关系，不表示语义支持关系。

## 状态与动作选择

任务覆盖代理 `C = min(已阅读的关联 URL 数 / target_sources, 1)`。
任务状态包括 covered、blocked、ready、exhausted。
未完成的先决任务会阻止后续任务；已用完查询且没有可读来源的任务标记 exhausted。

每个就绪任务产生一个候选动作：优先阅读尚未尝试的来源，否则使用下一条未尝试查询。
相同工具动作只尝试一次；失败也计入尝试历史，避免反复读取坏链接。
搜索和阅读使用相同的工具执行器，失败请求照常消耗工具预算。

- **static**：选择计划中第一个可执行且预算允许的候选动作。
- **adaptive**：每次证据更新后重新比较所有可执行候选动作，选择最大效用。

效用计算为：

```text
expected_proxy_gain = min(1 / target_sources, 1 - C)
score = priority × expected_proxy_gain / estimated_cost
```

READ 的预计成本为 1，SEARCH 为 2（搜索加至少一次阅读）。
预计成本同时必须落在剩余工具预算和决策步数之内；两种策略共用这项规则。
平分时按计划顺序稳定选择。分数、候选动作和最终选择写入每一步轨迹。

这是确定性的启发式调度：并不预测搜索能否成功，也没有学习到置信度或不确定性。
剩一个调用时不会启动新搜索，即使摘要可能有用；这是目前按正文阅读目标优化的保守设计。
所有任务覆盖后停止；没有可执行动作时也停止，并在报告列出未达标任务。

## 复现实验

```sh
.venv/bin/adra --snapshot data/planning/snapshot.json \
  --plan data/planning/plan.json --strategy adaptive --max-tools 4

.venv/bin/python -m adra.evaluation \
  --suite data/planning/suite.json --output outputs/planning-comparison-v1
```

输出目录必须尚不存在，避免覆盖实验。比较器保存原始 suite、SHA-256、依赖版本、
两种策略的运行配置、报告、轨迹和汇总表。真实延迟随运行变化，不要求字节级复现；
固定输入下动作、结果和覆盖代理可以复现。

包含五种**手工构造的合成场景**，每种分别运行 static/adaptive：

1. budget_tradeoff：任务目标大小不同，预算不足以覆盖全部任务。
2. dependency：文件中的任务顺序与依赖顺序不同，验证依赖约束。
3. empty_fallback：首次搜索为空，随后使用备选查询。
4. failed_read：一个正文不可读取，验证失败后转向其他任务。
5. shared_source：不同任务找到同一来源，验证共享、去重和历史状态不变性。

第一种场景中，static 达到 1/3 的任务平均来源覆盖，adaptive 达到 2/3。
这个例子刻意构造了有利于短任务调度的条件，只说明调度规则在工作，**不能证明算法更优**。
两种策略约束的预算上限相同，实际调用次数不一定相同。
报告质量、引用支持率仍为空；后续需要真实任务、语义覆盖验证和独立 Judge。

## 可选语义完成条件

通过 `--coverage-mode semantic` 可替换本文的来源数量完成条件。此时仅全部验收要点
被判断为 supported 才完成任务，缺口会驱动已有候选动作继续执行。完整规则见
[语义覆盖说明](semantic-coverage.md)。来源数量仍作为独立代理指标记录。
